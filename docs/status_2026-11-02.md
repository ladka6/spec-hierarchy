# Status 2026-11-02: what we measured and what comes next

Setup for all numbers below unless stated: target Qwen3-8B, drafter z-lab/Qwen3-8B-DFlash-b16 (block 16, 15 drafted
tokens), greedy (T=0), offline on the target's own greedy text. 20 prompts each from GSM8K, MATH-500, HumanEval,
MT-Bench, max 512 new tokens, an anchor every 8 tokens: 3471 blocks. "Accepted" = accepted tokens per verification
including the bonus token. "Fork" = DFlash's first wrong position in a block (everything before it right).

## 1. Batch-1 cost model

| component | cost |
|---|---|
| target verify, 1 / 16 / 32 / 64 / 128 / 256 nodes | 12.7 / 13.3 / 14.1 / 14.2 / 15.8 / 19.0 ms |
| DFlash drafter pass | 2.6 ms (bench_draft); 3.55 ms in bench_depth (CUDA graphs, other node) |
| 4-bit copy pass | ~4.5 ms |
| DFlash round (draft + verify 16) | 15.9 ms for ~8.0 accepted, ~0.50 tokens/ms |

Passes cost, width is nearly free. Each extra ms per round costs ~0.5 accepted tokens at DFlash's rate.

## 2. How DFlash fails

- Accepted ~7.97-8.03 per block; accuracy at a correct prefix 0.897, flat over block positions: a constant per-token
  hazard of ~10%, acceptance is compounding of it (exp96). No healing after the first error (exp96).
- At the fork the true token is DFlash's 2nd choice 0.56, in its top-3 0.72 (exp91, exp99), in top-16 80-99% (exp94).
- 57% of failures after the first position are fixed by a fresh DFlash block with real target features at the last
  correct token, i.e. they need target computation over the drafted tokens (exp94).
- In the target's own text a changed token mostly changes the next 1-3 tokens (exp95).
- DFlash's own confidence locates its fork with AUROC 0.925 (exp98).

## 3. Holes: is a fork a single decision? (exp91, infill-trained drafter)

| at DFlash's actual first error | accepted |
|---|---|
| plain | 8.03 |
| true token there, block redrafted around it in one pass | 10.23 (10.40 as tree with plain) |
| drafter top-2 / top-3 tokens there, one redraft each, tree with plain | 9.59 / 9.95 |
| true token at a fixed position m instead (best m = 4) | 8.52 (8.88 as tree) |

Yes: with the right token at the fork the rest of the block is easy again. Capped by the block length (redraft inside
the original 15 positions only).

## 5. The copy at DFlash's forks (exp99) - the key result

2775 forks in 3471 blocks.

| copy | fork top-1 | top-2 | top-3 | same mistake as DFlash | {copy top-1, DFlash top-2} | locator AUROC |
|---|---|---|---|---|---|---|
| bnb4 (4-bit NF4) | 0.883 | 0.982 | 0.996 | 0.064 | 0.942 | 0.997 |
| trained 4-bit copy (copy_lm_4bit) | 0.863 | 0.975 | 0.994 | 0.074 | 0.923 | 0.997 |
| rtn3 (simulated 3-bit) | 0.666 | 0.859 | 0.918 | 0.147 | 0.815 | 0.979 |
| 2-bit RTN + LoRA, LM loss (copy_lm) | 0.590 | 0.783 | 0.864 | 0.186 | 0.774 | 0.967 |
| 2-bit RTN + LoRA, both losses (copy_both) | 0.554 | 0.763 | 0.844 | 0.196 | 0.761 | 0.960 |
| rtn2 (simulated 2-bit) | 0.009 | 0.016 | 0.021 | 0.013 | 0.566 | 0.594 |

By the target's own margin at the fork (bnb4): 11% of forks are target near-ties (margin < 0.1): top-1 0.55, top-3
0.97; clear forks: top-1 0.92, top-3 0.999.
(The "overall agreement" column of exp99 counted prompt tokens too and is not meaningful; to be fixed.)

The copy resolves forks and locates them almost perfectly; it rarely shares DFlash's mistake. Fork accuracy falls
steeply with bits; training a 2-bit copy recovers part of it (0.01 -> 0.59).

## 6. Earlier results this builds on

- Copy refresh (draft, copy pass over the draft, refresh features, continue, verify): ~14.0 accepted per round.
- Hierarchy + trees: ~1.26x over DFlash sequential; ~2x ceiling with draft/verify overlap; batch-1 ceiling ~2x per
  16-token block.
- Copy margin locates DFlash errors better than DFlash's own confidence (0.97 vs 0.92, earlier copyeval).
- Closed lines (with reasons in the logs): alignment / anchors, point repair, healing, decorrelated drafts (beam,
  sampling, checkpoints, feature corruption, PARD as locator), G1, compression-for-role (feature-matching copy
  loss), learned 2-bit tap quantizer (exp88, too slow), deep narrow one-pass drafter (bench_depth, too slow per layer).

## 7. Fork model (performance model)

One copy-resolved fork per iteration: accepted ~ tau_D + a_F x tau', with tau_D ~8 (DFlash), a_F the copy's accuracy
at forks, tau' the continuation after the fork (assumed ~6-7, not yet measured). With bnb4: ~13.3-14.2, consistent
with the measured copy refresh ~14.0. Rough iteration table (top-1 only, ~7 ms per iteration): iteration 1 ~0.59
tokens/ms, iteration 2 ~0.60, iteration 3 flat. Top-k branching keeps coverage per iteration at ~0.98 instead of 0.88.

## 8. Method (agreed direction): fork-resolving block trees

1. DFlash drafts a block.
2. The copy runs once over each new block: fork position (first disagreement), its top-k at the fork, hidden states
   for the drafted prefix (approximate target features).
3. Fork gate: per fork, how many branches (0-3 of the copy's top-k) and whether to expand further. Scores branches by
   expected gain (P(path right) x P(branch token) x expected continuation), best-first under a node / pass budget.
   v1 rule-based, v2 small learned model on offline rollouts.
4. Continuation: DFlash drafts a full block from each opened branch with the copy's features, all branches in one
   batched pass. Repeat 2-4 while the gate expands.
5. The target verifies the tree of blocks once (original draft kept as a branch): lossless.

Training phases: (1) none, off-the-shelf drafter + 4-bit copy + rule gate; (2) learned gate, drafter fine-tuned to
continue from fork restarts with copy features; (3) fork-aware compression of the copy (loss weighted at DFlash's
forks, precision allocated by fork sensitivity).

Research questions: RQ1 where and why block drafters fail (forks); RQ2 can a compressed copy locate and resolve forks,
and how to grow the tree from them under batch-1 costs; RQ3 end-to-end batch-1 speedup and whether the fork model
predicts it; RQ4 compress the copy for the drafter's forks.
