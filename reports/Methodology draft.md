# Feature-refreshed drafting: methodology draft (13 October 2026)

Working draft. Unless stated otherwise, all numbers are offline measurements with Qwen3-8B as the target model and the public DFlash drafter for Qwen3-8B (block size 16). They are there to support the design choices, not as final results.

Terms used throughout:
- **Accepted length**: the number of tokens accepted per target verification pass, including the token the target adds itself. Higher is better; it is the main quality metric of speculative decoding.
- **Anchor**: the last committed position, from which the drafter predicts the next block.
- **Stop position**: the first position in a drafted block where the draft differs from the target, so acceptance stops there.
- **Features**: the target's hidden states at the five layers the DFlash drafter reads (layers 1, 9, 17, 25 and 33 of 36), which condition the drafter.

## 1. Setting and motivation

Block diffusion drafters such as DFlash [DFlash] predict a block of 16 tokens from the target's features at one anchor position. The tokens inside the block never receive target features, so the drafter has to guess the rest of the block from the anchor alone. Most of the recent work on block drafters (D2SD, DEdit, xPress, Domino, DSpark, DFlash 2) treats the resulting loss as a dependency problem between the drafted tokens and adds token conditioning, refiners or editing passes. The small experiments in Section 2 show that the larger part of the loss is something else: the target's computation over the drafted tokens is missing. The methodologies in Sections 4 to 6 are built on these findings.

## 2. Preliminary experiments

These measurements are made offline on texts generated by the target itself, so the correct continuation is known at every position.

**P1. Accuracy decays along the block.** The drafter's top-1 accuracy is 0.93 at the first position after the anchor and 0.37 at the fifteenth (greedy decoding, T=0). The first positions are reliable, the second half of the block is mostly lost.

**P2. Trees and dependency fixes saturate.** DDTree, which verifies a tree of candidate continuations built from the drafter's per-position distributions, grows only from 7.71 to 8.10 accepted tokens when the tree goes from 64 to 512 nodes. Our own attempts to model the dependency between drafted tokens (trees over several blocks, redrafting at the most uncertain position, a dependency head on the drafter) all stayed at +5 to 8% over DDTree. More candidates built from the same drafter distributions do not help much, so the right token is often not reachable from what the drafter knows.

**P3. What fixes a stop.** At every stop position we redrafted from that position, giving the drafter different information about the correct prefix:

| Redraft with | Stops fixed (64-node tree, T=0) | Stops fixed (T=1) |
|---|---|---|
| the correct prefix tokens only | 49% | 41% |
| features from only the first 18 target layers, on the correct prefix | 57% | 51% |
| real target features on the correct prefix | 80% | 68% |

The correct tokens fix about half of the stops, which is the most that a dependency fix can give, since it only adds information about tokens. The real features fix much more. 38% of the stops are at positions where the target itself is nearly certain (entropy below 0.1), and the real features fix 95.5% of these. These are not hard tokens; the drafter just lacks the information. DFlash's own ablation points the same way: removing the target features drops its accepted length on MATH-500 from 7.87 to 4.61.

**P4. A 4-bit copy gives features as good as the real ones.** Here the drafter restarts at the positions where it is most likely to stop, and the features for the drafted tokens come either from the target or from a quantized copy of the target that ran over the draft (plain DFlash: 7.98):

| Feature source | Accepted length |
|---|---|
| real target features | 12.54 |
| 4-bit copy | 12.53 |
| 3-bit copy | 12.09 |
| 2-bit copy (round to nearest, no training) | 8.44 |

The target computation that the drafter needs can be approximated by a low-bit copy without loss down to 3 bits.

**P5. Where the gain comes from.** The copy also predicts the next token at every position, so it can correct the draft at its first disagreement. We separated the parts of the gain (T=0, all trees of 31 nodes or less):

| Variant | Accepted length |
|---|---|
| plain DFlash | 7.98 |
| the copy's correction only (the copy used as an intermediate verifier) | 8.82 |
| correction, then the drafter continues from the corrected token without new features | 10.42 |
| correction, then the drafter continues with the copy's features | 14.25 |

About 13% of the gain is the correction (which quantized-verifier hierarchies such as QuantSpec and ML-SpecQD already use), 25% is redrafting after it and 61% is the copy's features. The same split holds at T=1.

**P6. Cheaper substitutes without training fail.** A small learned network that emulates the features from the drafted tokens (50M parameters) reached a cosine similarity of only 0.38 with the real features and fixed fewer stops than the tokens alone. Removing target layers without any training, keeping 24 or 18 of 36, loses most of the gain, and at 18 layers it is gone. Running the copy only in rounds where the drafter is uncertain lowered the acceptance more than it saved.

**P7. Verification width is almost free, sequential passes are not.** At batch size 1 the target's verification pass is limited by memory bandwidth, not compute. Measured in vLLM, it takes 12.7 ms for 1 token, 13.3 ms for 16, 14.1 ms for 32, 14.2 ms for 64, 15.8 ms for 128 and 19.0 ms for 256 tree nodes. A 4-bit copy pass costs 3 to 6 ms and a drafter pass 2.6 to 3.7 ms, every time it runs. In our own Hugging Face Transformers implementation with CUDA graphs, the copy cost 15.5 to 17.7 ms against 22.0 to 23.6 ms for the verification. There the method is around break-even (0.93 to 0.97x), because the per-layer overhead outside the matrix multiplications does not shrink with quantization.

**P8. Repeating the refresh helps, but sublinearly.** Repeating draft, copy and redraft several times before verifying raises the accepted length from 11.3 with one repetition to 19.0 with six (4-bit copy, T=1). Each repetition costs a full drafter and copy pass, and the best fixed or adaptive schedule reached 1.28x the speed of DFlash.

**From findings to design.** P3 to P5 motivate giving the drafter approximate target features for the drafted tokens (the refresh, Section 4). P7 says that extra work should go into width, more candidates verified in the same pass, rather than more sequential passes (Section 5). P8 says that more depth still pays in some rounds, so the number of repetitions has to be decided per round (Section 6). P6 and the copy cost in P7 motivate the analysis of cheaper copies in Section 8.

## 3. Common components

All methodologies below share the following components.

**Copy.** A low-bit copy of the target (4-bit weight-only quantization in the main setting). It processes the drafted block once and returns (i) the features at the drafter's five layers for the drafted positions and (ii) its own next-token prediction at every position. For the committed prefix the copy reads the target's key-value cache instead of its own, and it only computes the 16 drafted tokens itself. This sharing raised the copy's agreement with the target on drafted blocks from 0.940 to 0.954 for the 4-bit copy. For a 2-bit copy trained for this role (Section 8) it raised the accepted length from 12.70 to 13.02.

**Restart.** A restart is a new drafter call from a position inside the drafted block. It is conditioned on real target features up to the round's anchor and on the copy's features after it. All restarts of a round are packed into one batched drafter call.

**Verification and reset.** The target verifies the first block and all restarted continuations as one tree in a single pass. Under greedy decoding every emitted token is the target's own argmax, and under sampling the standard lossless tree acceptance is used, so the output distribution is exactly the target's. After verification the drafter's state is rolled back to the start of the round and rebuilt from the target's real features of the accepted tokens. The copy's features are used only inside the round and never enter the committed context.

**Cost model.** For projected speed we use measured vLLM component costs: verification 13.3 ms for 16 tokens, 14.1 ms for 32 and 14.2 ms for 64 tree nodes, drafter 2.6 to 3.7 ms, and 4-bit copy 3 to 6 ms (AWQ quantization with Marlin kernels). Because verification is memory bound at batch 1, a wider tree is almost free, while every extra sequential pass of the copy or the drafter costs its full latency. Speed is reported as accepted tokens per millisecond relative to plain DFlash.

## 4. Methodology A: single-pass refresh

One copy pass per round.

1. DFlash drafts the first block from the real target features.
2. The copy runs once over the drafted block (Section 3).
3. At the first position where the copy disagrees with the draft, the copy's token replaces the drafted token, and the drafter restarts from there with the copy's features (the correction restart). Optionally, a few extra restarts are placed at the positions where the drafter is most likely to stop, estimated from its own confidence (confidence restarts).
4. The target verifies the first block and the restarted continuations as one tree, and the drafter is reset to real features.

In the real decoding loop (greedy, 40 prompts from GSM8K, MATH-500, HumanEval and MT-Bench) the accepted length went from 5.86 for DFlash to 10.17 with the correction restart, and to 10.79 with two additional confidence restarts. DDTree with 64 nodes reached 7.52. As shown in P5, most of the gain comes from the copy's features, which is the part that existing quantized-verifier hierarchies [QuantSpec, ML-SpecQD] do not use.

## 5. Methodology B: wide refresh

Methodology A spends the copy pass on one correction. At batch 1 the verification cost hardly grows with the tree width (P7), so B uses the same single copy pass for many restarts, verified together.

From one copy pass the following restarts are built, all in one batched drafter call:

- **Second-guess restarts**: restarts from the copy's second and third most likely tokens at its first disagreement, since the copy is not always right at the position it doubts.
- **Later-disagreement restarts**: corrections at the copy's second and third disagreement positions, in case the first disagreement was the copy's own mistake.
- **Confidence restarts**: restarts at the K positions where the drafter is most likely to stop.

A policy is a combination of these. The best one combines the correction restart, one second-guess restart, one later-disagreement restart and two confidence restarts. Its tree has around 50 to 60 nodes, which costs about the same as a 64-node verification.

| Setting (4-bit copy) | Accepted length | Projected speed vs DFlash (copy at 3 ms) |
|---|---|---|
| T=0, best wide policy | 14.68 | 1.40x |
| T=1, best wide policy | 12.45 | 1.29x |
| T=1, best repeated refresh with a stopping rule (for comparison) | 14.2 | 1.28x |

One wide step reaches the same speed as the best repeated refresh at T=1, with a fixed and predictable cost per round, which makes it easier to implement in a serving engine. The tree has the same shape in every round, so it fits the tree attention kernels that already exist for EAGLE and DDTree.

## 6. Methodology C: adaptive repeated refresh

C repeats the refresh inside a round (draft, copy, redraft with the copy's features, copy again, ...) before verifying, and decides per round how many repetitions are worth their cost. The accepted length rises with the number of repetitions but sublinearly (P8), while every repetition adds a full drafter and copy pass. A fixed number of repetitions is therefore never the best choice, and the question is when to stop.

**Stopping rule.** After repetition r, the current best continuation has an estimated probability of being accepted up to each position, computed from the drafter's confidence and the copy's agreement with it. Let A_r be the expected accepted length under this estimate, c the cost of one more repetition (drafter plus copy), and T_r the time spent on the round so far. We continue while

    (A_{r+1} - A_r) / c  >  A_r / T_r

with A_{r+1} predicted from the positions where the drafter and the copy still disagree or the drafter's confidence is low. In words, we repeat while the expected gain per millisecond of one more repetition is larger than the average accepted tokens per millisecond of the round so far. A simpler threshold version stops once the estimated probability that the continuation is correct up to the end of the block is above a threshold; a threshold of 0.8 gave the best result so far (accepted length 14.2 and 1.28x at T=1).

**The same rule in A and B.** The same comparison also decides the work inside a single copy pass. If the copy agrees with the whole draft and the drafter is confident, no restart is made and only the first block is verified. In B, the number and kind of restarts are chosen by the same expected-gain-per-millisecond comparison, using the verification costs of the cost model. This makes the width and the depth of the refresh two settings of one decision instead of two separate methods.

Still open: the best possible stopping rule (an oracle that knows the accepted length after each repetition) has not been measured yet. This needs per-round logging and one more offline run.

## 7. Overlapping the copy with the verifier

The copy and drafter work of the next round can run on a second CUDA stream while the target verifies the current round, on the same GPU. In our Hugging Face Transformers implementation with CUDA graphs and a bitsandbytes 4-bit copy (which is slow at batch 1), the target verification alone took 22.4 ms, the drafter and copy work alone 39.4 ms, and both together 52.6 ms. So 23% of the small work was hidden behind the verification. With a fast 4-bit kernel the small work is shorter than the verification and a larger share should be hidden. Including partial overlap, the projected speed is about 1.5x at T=0 and 1.4x at T=1 over DFlash. A measured speedup needs the method inside vLLM, which is the main engineering item.

## 8. Analysis: how cheap can the copy be

The copy cost is the main overhead, so we studied whether a cheaper copy can give the same features. In this test the drafter drafts a block, the copy runs over it, the drafter redrafts from the two positions where it is most likely to fail using the copy's features, and the target checks everything in one pass. The table gives the accepted length for each copy, and how much of the 4-bit copy's result it keeps.

| Copy | Accepted length | Share of 4-bit |
|---|---|---|
| 4-bit, no training | 11.90 | 100% |
| 2-bit, no training | 8.34 | 70% |
| 2-bit, trained | 11.19 | 94% |
| 18 of 36 layers, trained | 10.45 | 88% |
| 8 of 36 layers, no training | 8.30 | 70% |
| 8 of 36 layers, trained | 9.20 | 77% |
| 8 of 36 layers + small modules replacing the removed layers, trained | 9.69 | 81% |

The "8 of 36 layers" copies keep only the layers whose outputs the drafter reads, plus the first and the last two layers. Training is described below. Without training a 2-bit copy loses 30%; with training it keeps 94% of the 4-bit result.

Three ways to make the copy cheaper were tested.

1. **A copy trained for its role.** Low-rank adapters (LoRA) on a cheap copy, trained so that the drafter's predictions with the copy's features match its predictions with the real features (a KL loss on the drafter's top-32 tokens), plus a loss on the copy's agreement with the target's next token. This recovers most of the 2-bit copy (8.34 to 11.19) but not the copies with removed layers.
2. **The drafter's layers with small replacement modules.** The copy keeps only the 8 layers above and replaces each removed span of 7 layers by a small module. Each module starts from a closed-form linear fit of what the removed span adds to the hidden state (ridge regression, following Ghosted Layers [2605.15491] and SHIFT-LLM [2608.25068]), and is then trained with a hidden-state loss, the drafter loss and the agreement loss. Without these modules the copy is unusable: the drafter's predictions with its features agree with those with real features only 3% of the time. The linear fit brings this to 20 to 24% and training to 31%. The accepted length reaches 9.69, better than the trained 8-layer copy without modules, but still only 81% of the 4-bit copy. Fitting each module on the copy's own inputs, with the earlier modules already in place, is a better start than fitting every span independently as in the original papers, because the errors of the four removed spans add up.
3. **A drafter that learns how much to trust approximate features.** Following DFlow [2609.06498], the copy's features after a restart position were given to the drafter as additional input at the positions it has to predict, scaled by a small trained gate, with the drafter itself frozen. This gave no gain with the 4-bit copy (10.60 to 10.63) and a small loss with the 8-layer copy with modules (7.46 to 7.38). The frozen drafter cannot use extra signals at positions where it never saw any during its training.

The conclusion of this analysis is that the drafter needs features close to the real ones. From the cost model, a copy at half the cost of the 4-bit copy only pays off if it keeps about 93% of the 4-bit copy's accepted length, and none of the cheaper copies reached that. The 4-bit copy is therefore the copy of the main method, and this analysis explains why the cheaper alternatives fall short.

## 9. Evaluation plan

- Targets: Qwen3-8B (main), Qwen3-4B, and one LLaMA model if a DFlash drafter is available.
- Data: GSM8K, MATH-500, HumanEval, MBPP, MT-Bench, Alpaca.
- Temperatures: T=0 and T=1 (lossless tree sampling).
- Baselines: DFlash, DDTree, DFlow, a quantized-verifier hierarchy where the copy only verifies (QuantSpec style), and EAGLE-3 where available.
- Metrics: accepted length, projected speed from the cost model, and measured speed in vLLM for the final method.
- Ablations: correction only against redrafting against the copy's features (A); each restart type (B); fixed repetitions against the stopping rule against the oracle (C); sharing the target's cache on and off; overlap on and off.

## 10. Limitations

- The speed numbers are projections from component costs. Our Hugging Face implementation is around break-even because the per-layer overhead does not shrink with quantization.
- The 4-bit copy needs about 5 GB of extra memory, which matters at larger batch sizes. At larger batch sizes the verification is also no longer memory bound, so the free width of Methodology B shrinks.
- The cheaper copies were trained with little data (2,400 sequences, one epoch). The conclusions in Section 8 hold for this budget; a larger training run could change them.
- All results so far are with Qwen3-8B and its DFlash drafter.
